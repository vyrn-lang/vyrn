# RFC-0126 — a type constructor is a case in every pass

- **Status:** Census closed (2026-09-04); the `Option`/`Result` collapse it
  ranked first is designed in §8, and §8.7's first step is Implemented
  (2026-09-04). The census is still the deliverable, it is still pinned by
  `compiler/vyrn-cli/tests/surface.rs`, and the ranked collapses in §5 each say
  what they would cost. Two defects it found are fixed: `Type::Stream`'s doc
  comment in `ast.rs` claimed a lowering the code stopped using at RFC-0075 M2b
  (§6), and the "no nested Option/Result" rule refused a type all three engines
  already ran (§8.7).
- **Depends on:** RFC-0125 §2.8, which deferred this census and named its
  candidates; RFC-0082 (containers are Vyrn — the array and Map collapses were
  already attempted, and the numbers that stopped them are quoted here);
  RFC-0091 M4 (the `SmallArray` port, stopped a third time); RFC-0056, RFC-0028,
  RFC-0075, RFC-0083, RFC-0085 M4a and RFC-0079, which are what the rows cite.
- **Evidence:** the counts in §3, measured at this branch's tip by the method in
  §2 and recomputed by `tests/surface.rs` on every run; the layout table in
  `vyrn-codegen/src/lib.rs`'s `llt_of`; `vyrn-frontend/src/types.rs`'s `resolve`;
  RFC-0082's own gate numbers.

---

## 1. The question

RFC-0125 §2.8 wrote the surface out of its own scope and said what it thought
was there:

> **The surface census.** Three array kinds, three Map key kinds, and several
> result-like types can become library over fixed arrays and canonical packs.
> Each is a checker case that becomes a desugar. A later RFC, done while the
> compiler is still in Rust and easy to change.

This is that RFC. It measures every constructor of `ast::Type`, one row each,
and gives each a verdict. The paragraph above is treated as a hypothesis, not as
a finding, because two of its three candidates have already been tried and
stopped with numbers on the record.

§1.1 of RFC-0125 says the size is `(surface × types × builtins × engines)`. The
`types` factor is 35 constructors. This census prices that factor.

---

## 2. The method, so a number can be re-derived

A constructor's cost is measured as the number of times its name appears as
`Type::<Name>` in the seven files that carry the language's decisions. The rule
is mechanical, and `tests/surface.rs` applies exactly it:

1. A line whose trimmed text starts with `//` is skipped, so a doc comment that
   names a constructor is not a case.
2. An item annotated `#[cfg(test)]` is skipped whole — from that line to the
   line closing the first brace opened at or after it. A fixture in a test
   module is not a pass.
3. In what is left, `Type::<Name>` is counted where the next character is not a
   letter, digit or underscore. That is what keeps `Type::Int` from counting
   `Type::IntN`, and `Type::Array` from counting `Type::ArrayN`.

**A mention, not an arm.** A `match` arm, a construction and a `matches!` each
count as one. Counting arms alone would need a Rust parser and would
under-report: a constructor the checker *builds* in twelve places is stated
twelve times, and each is a place a collapse has to change. The unit is
therefore "the constructor is named here".

The seven files, and why each:

| column | file | what it decides |
|---|---|---|
| `checker` | `vyrn-frontend/src/checker.rs` | what a program means |
| `interp` | `vyrn-frontend/src/interp.rs` | the interpreter's engine |
| `native` | `vyrn-codegen/src/lib.rs` | the textual-IR emitter, and `llt_of` |
| `wasm` | `vyrn-codegen/src/direct.rs` | the direct wasm emitter |
| `types` | `vyrn-frontend/src/types.rs` | `resolve`, `substitute`, `solve_param` |
| `prelude` | `vyrn-frontend/src/prelude.rs` | the seeded builtin signatures |
| `editor` | `vyrn-frontend/src/symbols.rs` | the per-type method and hover tables |

`prelude` and `editor` together are the "builtin rows that exist only for this
constructor" column the census was asked for. They are counted the same way as
the rest rather than as rows, for one reason: a row is not a unit anybody can
compare across files, and one metric that means the same thing in seven places
is worth more than two metrics that each mean something else in one.

**What this leaves out on purpose.** `own.rs`, `movecheck.rs`, `parser.rs`,
`codec.rs`, `loader.rs` and the lowered form add about a thousand more mentions.
They are downstream of the seven: no collapse can delete a case there that it
does not first delete here, so the seven are the ones that decide, and adding
the rest would move every row by roughly the same factor without changing an
order.

### 3.1 What the `interp` column is not

The interpreter's column is small everywhere, and it does not mean the
interpreter is cheap. The interpreter has no types at runtime: its cost is in
`Val`, and `Val` has 23 variants of its own. Read that way the column is the
most useful one in the table, because the interpreter is the one engine that has
already answered §2.8's questions by building a representation:

| `Type` constructors | the `Val` they become | what that says |
|---|---|---|
| `Array`, `ArrayN`, `SmallArray` | `Val::Array` | the three array kinds ARE one at runtime, in one engine |
| `Map` | `Val::Map`, `Val::MapI`, `Val::MapU` | one constructor is THREE representations (RFC-0117) |
| `Stream` | `Val::Stream` | not `Val::Array` since RFC-0075 M2b — see §6 |
| `Fn`, `Lazy` | `Val::Fn` | `resolve` already answers `Fn([], T)` for a `lazy T` |
| `Named`, `App`, `Omit`, `Pick`, `Merge`, `Partial` | whatever they resolve to | no representation of their own |
| `ConstInt`, `Never`, `Err`, `Param`, `Task`, `Logger` | none | a compile-time constructor, or another `Val` |

So §2.8's two headline candidates point in opposite directions. The three array
kinds are already ONE representation in the interpreter and three in the
compiled backends. The three Map key kinds are ONE constructor and three
representations everywhere. A census of the surface prices the first; the second
is not a surface question at all.

### 3.2 The layout is already stated once

`llt_of` in `vyrn-codegen/src/lib.rs` is one `match` from a type to an LLVM
shape, and `layout::of_ll` parses what it prints, so the direct wasm backend
reads that table rather than keeping one. The census agrees: no constructor has
a second layout statement in `direct.rs`. RFC-0101 M5's work is holding. What
the two compiled backends still duplicate is the OPERATIONS on a shape, not the
shape.

## 4. The verdict, one row each

`stays` — the constructor is irreducible, or a measurement already refused the
collapse. `desugar` — another constructor already expresses it and the compiler
computes that expansion today. `decide` — a collapse exists and something has to
be chosen first; the row says what.

| constructor | what it is | RFC | verdict | the desugar, or the reason |
|---|---|---|---|---|
| `Type::Int` | the 64-bit signed default | RFC-0002 | stays | `IntN{64,true}` is never built — the parser maps `Int64` here — so the merge renames 182 sites and removes no rule |
| `Type::IntN` | a sized integer | RFC-0002 | stays | four widths and two signs in one constructor: it is already the collapse |
| `Type::Float` | 64-bit IEEE-754 | RFC-0002 | stays | the default float, as `Int` is the default integer |
| `Type::Float32` | 32-bit IEEE-754 | RFC-0002 | decide | `FloatN{bits}` would do to floats what `IntN` did to integers; decide first whether the two widths differ by more than a width at the coercion ladder |
| `Type::F32x4` | four `Float32` lanes | RFC-0083 | stays | a value with its own representation and its own opcodes |
| `Type::I32x4` | four `Int32` lanes | RFC-0083 | stays | no divide, no sqrt, and it gains the bitwise operators — a different operation set, not a different lane |
| `Type::F64x2` | two `Float64` lanes | RFC-0083 | stays | the width explicit SIMD exists for |
| `Type::Mask32x4` | four `Bool` lanes | RFC-0083 | decide | one `Mask{lanes}` constructor saves 43 mentions; RFC-0083 argued that the SURFACE should not spell `Mask<N>`, and said nothing about the AST |
| `Type::Mask64x2` | two `Bool` lanes | RFC-0083 | decide | the row above, and the same decision; the two are one |
| `Type::Bool` | a boolean | RFC-0002 | stays | `i1`, and the type every condition has |
| `Type::Str` | a UTF-8 string | RFC-0002 | decide | it could be a validated `Array<UInt8>` — RFC-0082's boundary allows it, since a String owns its buffer — but it is 242 mentions, every literal and interpolation, and all of `std/strings`; decide whether the UTF-8 invariant is a validated type before pricing the port |
| `Type::Unit` | no value | RFC-0002 | stays | `void`, and what every statement returns |
| `Type::Named` | a declared type by name | RFC-0003 | stays | `resolve` expands it, but a recursive declaration has no finite expansion, so the name has to survive |
| `Type::Option` | `Option<T>` | RFC-0005 | decide | it is `enum { None, Some(T) }` and could be `Type::Enum`; the layouts differ (`{ i1, i64, i64 }` against `{ i64, i64… }`), and `?`, `if let` and every optional projection are typed on it — decide whether the two-word payload earns a constructor |
| `Type::Result` | `Result<T, E>` | RFC-0005 | decide | the row above, and the same layout; the two are one decision |
| `Type::Record` | a structural record | RFC-0002 | stays | the constructor the four transformers desugar INTO |
| `Type::Omit` | `Omit<T, f…>` | RFC-0002 | desugar | `Type::Record` — `types::resolve` computes it already; §5.2 says what stops the deletion |
| `Type::Pick` | `Pick<T, f…>` | RFC-0002 | desugar | `Type::Record`, the same way |
| `Type::Merge` | `Merge<A, B>` | RFC-0002 | desugar | `Type::Record`, the same way |
| `Type::Partial` | `Partial<T>` | RFC-0002 | desugar | `Type::Record` with each field wrapped in `Option` |
| `Type::Enum` | a sum type | RFC-0002 | stays | the constructor `Option` and `Result` would desugar into |
| `Type::Param` | a generic parameter | RFC-0002 | stays | substituted at each call site; nothing else names an unknown |
| `Type::App` | `Box<Int>` | RFC-0002 | stays | `resolve` substitutes it, and a recursive generic has no finite expansion — `Named`'s reason one level up |
| `Type::Array` | a growable heap array | RFC-0002 | stays | RFC-0082: you cannot write the thing that allocates memory in terms of itself |
| `Type::ArrayN` | `Array<T, N>`, a value aggregate | RFC-0002 | stays | the type of an array literal, and the base §2.8 wants everything else written over |
| `Type::SmallArray` | `SmallArray<T, N>` | RFC-0056 | stays | measured: RFC-0082 "Where the thesis stops" — inline capacity is uninitialized memory, three language features are missing, and the nearest expressible container ran 1.8x slower on a push, 7.9x slower on an indexed read, with 13% more wasm |
| `Type::ConstInt` | the `8` in a type argument | RFC-0056 | decide | the parser could read the literal at the type-argument site and never build the node; then its two refusals become parse errors, and a parse error stops the file where a checker error accumulates (RFC-0006) — decide whether those two diagnostics may become fatal |
| `Type::Map` | `Map<K, V>` | RFC-0028 | stays | measured: RFC-0082 M3 withdrew Map over Array at 18x on the interpreter. The three KEY kinds are a representation split, not a surface one — the constructor is already one |
| `Type::Stream` | a linear sequence | RFC-0075 | stays | not `Array` any more: since M2b it is a six-word tagged header over two producers, with a `Val::Stream` of its own (§6) |
| `Type::Task` | a task handle | RFC-0025 | stays | `spawn` produces it and `join` consumes it; erasing it erases the obligation to join |
| `Type::Logger` | a logger handle | RFC-0008 | decide | eleven mentions and five methods over what is a pointer to a name string; `impl` blocks make a library `Logger` expressible (RFC-0080, RFC-0084) — decide where RFC-0008's level filtering lives if the five methods become ordinary functions |
| `Type::Fn` | a function value | RFC-0023 | stays | defunctionalized to `{ tag, payload }` (RFC-0037); the constructor `Lazy` desugars into |
| `Type::Lazy` | a deferred field | RFC-0085 | desugar | `Type::Fn([], T)` — `types::resolve` answers exactly that already; §5.1 says what stops the deletion |
| `Type::Never` | the bottom type | RFC-0079 | stays | `assignable(Never, _)` holds and the reverse does not; no other constructor has that rule |
| `Type::Err` | the recovery sentinel | RFC-0006 | stays | 138 of its 141 mentions are the checker carrying on after an error it already reported |

Of the 35 rows, 5 say `desugar`, 8 say `decide` and 22 say `stays`.

## 5. The ranked collapses, and why none is taken

Cheapest first. "Saved" is the census total for the constructors deleted.

### 5.1 `Type::Lazy` into `Type::Fn([], T)` — 21 saved, and the marker does not fit

`resolve` already answers `Fn([], T)` for a `lazy T`, so no engine has a layout,
an ownership rule or a dispatcher for it. The constructor survives only as a
MARKER: `lazy` is legal in field position and nowhere else, and three passes
must still see it — the field read, which forces; the codec, which forces too;
and reflection.

The marker's only other carrier is `ast::Field`, a two-field struct built in
**246 places** across the workspace. Adding a third field edits every one of
them, or hides them behind a constructor and a `Default`. That diff is larger
than the 21 mentions it removes, and it moves a fact out of the type that
carries it into a struct that does not. **Not taken, and it should not be taken
until `Field` grows a constructor for some other reason.**

### 5.2 `Omit`/`Pick`/`Merge`/`Partial` into `Type::Record` — 69 saved, blocked by generics

The four are pure functions of a field list, `resolve` computes each, and no
engine gives any of them a representation: `llt_of` answers `void` and its own
comment calls the arm unreachable. So the move is to compute them ONCE, in the
loader, after the type table exists, and delete every downstream arm.

It does not work, and the blocker is one line in `resolve`: the expansion needs
the base's field list, and a transformer over a bare type parameter has none —
`fields_d` answers `None` and the result is `Type::Unit`. A generic declaration
(`type P<T> = Partial<T>`) therefore cannot be folded until it is instantiated,
which is what `resolve` at each use already is.

**The gate this needs, stated so a later slice can take it:** refuse a
transformer over a bare type parameter, with a diagnostic, and the loader's fold
becomes total. The corpus does not write one today —
`examples/utility.vyrn` is the only file that uses a transformer at all, and its
three uses all name a concrete type. That is a language decision, not a
refactor, so it is not taken here.

### 5.3 `Type::ConstInt` into the type-argument parse — 7 saved, a worse first error

Seven mentions, and the node exists only to carry `N` from the parser to
`SmallArray`. The parser could read the literal at the type-argument site and
never build a node. Its two refusals — `Box<3>`, and a bare integer in a type
position nothing consumes — would then be parse errors. RFC-0006's accumulation
is what that costs: a checker error reports and continues, a parse error stops
the file. Seven mentions do not buy a worse first error. **Not taken.**

### 5.4 `Float`/`Float32` into `FloatN{bits}` — 154 touched, 0 saved

A rename, not a collapse: every arm gains a width guard and no rule is deleted.
`IntN` did this and kept `Int` separate for the same reason. **Not taken.**

### 5.5 `Option`/`Result` into `Type::Enum` — 205 saved, and it changes bytes

The largest real prize in the table, and the one with the most rules attached.
Both lower to `{ i1, i64, i64 }`; a user enum lowers to `{ i64, i64… }` with one
payload slot per the widest variant. The collapse changes the tag width and the
payload count in both compiled backends and both `Val` variants in the
interpreter, and `?`, `if let`, refutable `let`, `tryField` and every optional
projection are typed against the constructors. That is a milestone, not a slice.
**Not taken as a slice. §8 designs it, prices it again from measurements
instead of from the table alone, and takes the one step the measurements
license.**

### 5.6 The two §2.8 named that are already refused

`SmallArray` and `Map` are not open questions. RFC-0082 M3 withdrew Map over
Array at 18x on the interpreter. RFC-0091 M4 resumed the `SmallArray` port and
stopped: three missing language features, and the nearest expressible container
measured 1.8x and 7.9x slower with 13% more wasm. RFC-0082 states the boundary
in its own words — a container whose spare capacity is a heap buffer it owns can
be Vyrn, a container whose spare capacity is inline cannot — and `SmallArray` is
on the far side of it.

**So §2.8's paragraph is two-thirds wrong, and saying so is what this census was
for.** "Three array kinds" is one measured refusal (`SmallArray`), one
irreducible primitive (`Array`) and one base that everything else would be
written over (`ArrayN`). "Three Map key kinds" is not a surface question at all:
it is one constructor and three representations. The third — "several
result-like types" — is real, is §5.5, and is the most expensive item in the
table.

## 6. The defect the census found

`ast.rs`'s doc comment for `Type::Stream` said the lowering is `Array<T>`'s
exactly, in all three engines: `{ ptr data, i64 len, i64 cap }`, `Val::Array`,
and the same indexed walk for `for … in`. RFC-0075 M2b changed all three and the
comment did not follow. `llt_of` answers `{ ptr, i64, i64, i64, i64, i64 }` — a
six-word tagged header over two producers — and the interpreter has a
`Val::Stream` holding a `StreamVal` of its own. A reader pricing the Stream
collapse from that comment would have priced a free one. The comment now says
what the code does, and cites M2b for the change.

RFC-0125 §1.6 already records the general form: about 30% of every large file is
prose that retells an RFC, and prose does not compile.

## 7. What this RFC does not decide

- **Whether the other collapses should be taken.** Six rows say `decide` and
  each names its decision. Only §5.5's is designed (§8); a later slice that
  takes one of the rest has this table to move.
- **The `Val` census.** §3.1 maps the constructors onto the interpreter's 23
  variants but does not price them. The interpreter is what RFC-0125 §2.7
  deletes, so pricing it belongs to that milestone.
- **The thousand mentions outside the seven files.** §2 says why they are left
  out and why leaving them out changes no order.

## 8. The `Option`/`Result` collapse, designed

§5.5 ranked this first and stopped at the table. The table is not enough to
decide it: the row says the two layouts differ, and it does not say which is
better, what the difference costs, or in which direction. This section measures
that, states what the two constructors become, writes the bytes out before and
after for every engine, and orders the migration. §8.7 takes the first step.

### 8.1 What the two constructors become

```
Option<T>       ->  Type::Enum([ EnumVariant { None, [] },
                                 EnumVariant { Some, [T] } ])
Result<T, E>    ->  Type::Enum([ EnumVariant { Err,  [E] },
                                 EnumVariant { Ok,   [T] } ])
```

The order is the TAG order and it is fixed by what exists. `Pattern::Failure`
is the tag-0 arm and `Pattern::Success` is the tag-1 arm (RFC-0079's `??`
desugar names them that way, in the parser, without a type). So `None` and
`Err` are variant 0 and nothing has to move.

**One layer already did this.** `codec::wire` answers
`Wire::Enum([Ok(T), Err(E)])` for a `Result` today, and its own comment says
why: "every consumer gets the tagging rule once instead of four times". A wire
tag is a NAME, not an index, so the codec is free to list `Ok` first. Nothing
below the wire is.

`Option` keeps a wire form of its own — `null` — and that is a real difference,
not a leftover. It is why §8.6's last step keeps a spelling rule after it
deletes the constructors.

### 8.2 The representation now, byte for byte

`llt_of` in `vyrn-codegen/src/lib.rs` is the only type-to-shape match (§3.2),
and the direct wasm backend reads its spellings back through `layout::of_ll`.
So one table serves both compiled engines.

| type | `llt` | size | align | interpreter |
|---|---|---|---|---|
| `Option<T>` | `{ i1, i64, i64 }` | 24 | 8 | `Val::Option(Option<Box<Val>>)` |
| `Result<T, E>` | `{ i1, i64, i64 }` | 24 | 8 | `Val::Result(bool, Box<Val>)` |
| enum, widest variant 0 payloads | `{ i64 }` | 8 | 8 | `Val::Enum(String, [])` |
| enum, widest variant 1 payload | `{ i64, i64 }` | 16 | 8 | `Val::Enum(String, [v])` |
| enum, widest variant 3 payloads | `{ i64, i64, i64, i64 }` | 32 | 8 | `Val::Enum(String, [a,b,c])` |

Two differences, and they are independent:

**The tag.** `i1` for the built-in sums, `i64` for a user enum. In bytes this is
a wash at every payload count above zero — `{ i1, i64 }` and `{ i64, i64 }` are
both 16 — because the first member pads to the aggregate's 8-byte alignment
either way. It only shows in the code: a built-in sum branches on `br i1`, an
enum on a `switch i64`.

**The payload slots.** Two fixed words for the built-in sums, one word per
payload slot of the widest variant for an enum. This is where the bytes are,
and it is also where the heap is, because the two conventions encode a payload
differently:

| payload | built-in sum (`encode_payload`) | user enum (`box_payload`) |
|---|---|---|
| `Int64` | word 0 | the slot |
| `Bool` | `zext` into word 0 | **malloc, pointer in the slot** |
| `String` | `ptrtoint` into word 0 | **malloc, pointer in the slot** |
| `Float64` | word 0 (bits) in wasm | **malloc**, and boxed in wasm too |
| a stored `fn` (`{ i64, i64 }`) | words 0 and 1, no heap | **malloc, pointer in the slot** |
| a record, an `Array`, a `Map` | malloc, pointer in word 0 | malloc, pointer in the slot |

`box_payload`'s whole test is `llt(t) == "i64"`. Anything else is malloc'd. The
direct wasm backend states the same split under two names — `word2` for a
built-in sum has five cases (`Direct`, `Ext`, `Float`, `Inline2`, `Boxed`) and
`word1` for an enum has two (`Direct`, `Boxed`).

### 8.3 The measurement: the two conventions differ twice, in opposite directions

Three probes, each the smallest program that shows one difference, each read
out of the emitted IR and run on all three engines.

**A scalar payload in an array.** `Array<Option<Int64>>` against
`Array<Maybe>`, where `type Maybe = | Nothing | Just(Int64)`. The literal is
one heap block either way:

```
%t8  = insertvalue [3 x { i1, i64, i64 }] ...   ; 72 bytes
%t8  = insertvalue [3 x { i64, i64 }] ...       ; 48 bytes
```

The enum convention is **8 bytes per value cheaper**, and an array of them is
33% smaller.

**A two-word payload.** `Option<IntSink>` against `Sink(IntSink)`, where
`type IntSink = fn(Int64)`. The built-in sum splits the fn value across its two
words:

```
%t5 = insertvalue { i1, i64, i64 } %t4, i64 %t2, 1
%t6 = insertvalue { i1, i64, i64 } %t5, i64 %t3, 2
```

The enum boxes it, reads it back through a pointer, and frees it at the drop:

```
%t10 = call ptr @__vyrn_malloc(i64 %t9)
store { i64, i64 } %t8, ptr %t10
...
%t5  = load { i64, i64 }, ptr %t4          ; the match
call void @__vyrn_free(ptr %t16)           ; the drop
```

The built-in convention is **one malloc and one free per value cheaper**.

**A one-word payload that is not an `i64`.** `Option<String>` against
`Word(String)`. The built-in sum casts; the enum mallocs 8 bytes to hold a
pointer:

```
%t0 = ptrtoint ptr ... to i64                          ; Some("a")
%t5 = call ptr @__vyrn_malloc(i64 %t4)                 ; Word("b")
store ptr ..., ptr %t5
```

That is not a corner: a `String` payload is the commonest enum payload in the
corpus. `Bool`, `Float64` and every sized integer pay the same.

**So neither convention dominates.** Max-arity slots cost every payload wider
than a word a heap round trip. Two fixed slots cost every one-word payload 8
bytes. A collapse that picks either one makes something worse, which is what
§5.5 meant by "it changes bytes" and did not say.

### 8.4 The rule that dominates both

Pick the tag the enum already uses, and make the SLOT COUNT a function of the
payload's width instead of the variant's arity:

- **tag:** `i64`, always. It costs nothing — §8.2 — and it removes the
  question.
- **slots:** the maximum over the variants of the sum over that variant's
  payload types of `words(t)`, where `words(t)` is 2 when `llt(t)` is
  `{ i64, i64 }` and 1 otherwise.
- **encoding:** `encode_payload`'s five cases, for every sum. A payload that
  fits its slots rides in them; a wider one is boxed, as both conventions
  already box a record.

Every shape under the new rule, against the same shape today:

| type | slots | shape | size | today | change |
|---|---|---|---|---|---|
| `Option<Int64>` | 1 | `{ i64, i64 }` | 16 | 24 | −8 bytes |
| `Result<String, String>` | 1 | `{ i64, i64 }` | 16 | 24 | −8 bytes |
| `Option<fn(Int64)>` | 2 | `{ i64, i64, i64 }` | 24 | 24 | none |
| `Option<Point>` (two `Int64`s) | 2 | `{ i64, i64, i64 }` | 24 | 24 | none, and native's box goes |
| `Maybe` (1 word) | 1 | `{ i64, i64 }` | 16 | 16 | none, and the box goes |
| `Tagged` (`String`) | 1 | `{ i64, i64 }` | 16 | 16 | −1 malloc, −1 free |
| `MaybeSink` (a stored `fn`) | 2 | `{ i64, i64, i64 }` | 24 | 16 | +8 bytes, −1 malloc, −1 free |
| `Bag` (5 variants, widest 2) | 2 | `{ i64, i64, i64 }` | 24 | 24 | none |

No row grows a heap round trip and one row grows 8 bytes. Every other row
shrinks, loses an allocation, or stays.

**What it costs.** Every module's wasm hash moves, because every sum in the
corpus changes shape or encoding. `layout::SHAPES` loses its
`("Option/Result", "{ i1, i64, i64 }")` row and gains the wider enum shapes.
`llt_of` loses one arm. Both engines lose one payload encoder each: native's
`box_payload`/`unbox_payload` fold into `encode_payload`/`decode_payload`, and
wasm's `word1` folds into `word2`.

### 8.5 What the census's 205 is worth

Two corrections, both derived from the census's own method (§2), and both
lowering the number:

**A construction is not an arm.** §2 counts a construction as a mention on
purpose, and for most constructors that is right. Here it over-reads, because a
construction does not disappear when the constructor does — it becomes a longer
`Type::Enum(vec![EnumVariant { .. }, ..])`, or it hides behind a helper. A
helper is not spelled `Type::<Name>`, so the counter stops counting it, and the
metric is satisfied by a rename that simplifies nothing. Measured over the
seven files by a raw grep — comments and test fixtures included, so higher than
the census's own 205 — 218 mentions of the two constructors, of which 81 are
`Type::Option(Box::new` or `Type::Result(Box::new`. **37% are constructions.**

**`Type::Enum` gains what the two lose.** Three places must still tell a
built-in sum from a user one after the collapse: the surface spelling in a
diagnostic (`Option<Int64>`, not `enum { None, Some(Int64) }`), the codec's
`Wire::Option` and its `null`, and `Some`/`Ok`/`Err` as constructor names the
parser accepts without a declaration. Each becomes a guard on `Type::Enum`,
where today it is a constructor.

So the honest reading of §5.5's number is: **205 mentions named, about 150 of
them arms a collapse deletes, and `Type::Enum`'s own 57 rising.** That is still
the largest item in the table by a wide margin, and it is not 205.

### 8.6 The migration, one step per commit

Each step compiles, gates and ships on its own.

**M1 — the nested refusal goes.** The checker refused `Option<Option<T>>`,
which a user enum has always allowed. §8.7 measured that all three engines
already ran it, took the step, and priced it: **16 mentions, one function, zero
bytes.** Done, 2026-09-04.

**M2 — one payload encoding per engine.** §8.4's rule. `box_payload` and
`unbox_payload` fold into `encode_payload` and `decode_payload`; `word1` folds
into `word2`; the slot count becomes a function of payload width. This is the
step that changes bytes, and it is the only one that does. It saves 0 mentions
and deletes 4 functions across the two backends. Every module's wasm hash
moves once, here, and `VYRN_WASM_MANIFEST` is regenerated in this commit and no
other. §8.9 took the step and priced it: **five functions, 55 code lines, 143 of
174 wasm hashes moved, and one rung the rule needed that this paragraph did not
foresee.** Done, 2026-09-05.

**M3 — the patterns.** `Pattern::Some`/`None`/`Ok`/`Err` become
`Pattern::Variant`. `Success` and `Failure` stay: they are the parser's untyped
arms for `??` and `?`, they name a TAG and not a variant, and nothing else can
name a tag before the checker runs. Surface only; zero bytes; priced in
`Pattern` arms, which the census does not count. §8.10 took the step: **four
constructors, 89 mentions to 0, 19 code lines, zero bytes.** Done, 2026-09-05.

**M4 — `resolve` answers `Enum`.** As it already answers `Fn([], T)` for a
`lazy T` (§4). Every engine calls `resolve` before it looks at a type, so
`llt_of`, `repr` and `sum_of` all see one constructor from this commit on.
**`solve_param` must gain a `Type::Enum` arm first — it has none today**, so a
generic `Option<T>` reaching it as an enum would solve nothing and
`applied_type` would fill the parameter with `Unit`. That gap is this step's
whole risk and it is one arm.
**Not taken, and both sentences above are wrong.** §8.11 measured it:
`solve_param` HAS that arm, the risk is elsewhere, and the step is neither one
arm nor zero bytes. Read §8.11 before this paragraph.

**M5 — delete the constructors.** The 205. `Display` recognises the two variant
lists and keeps printing `Option<T>` and `Result<T, E>`; `codec::wire`
recognises them and keeps `Wire::Option`; the parser keeps `Some`/`Ok`/`Err` as
declaration-free constructor names. Three guards where there were two
constructors. **Not taken: §8.11 shows this step and M4 are one step, and that a
third — one EMISSION per engine — belongs in front of both.** The three guards
above are unaffected and still stand.

### 8.7 M1, taken: the nested refusal was conservatism

The checker refused a nested built-in sum in three places, with one message —
"nested Option/Result is not supported in v0.1" — and one helper,
`has_nested_wrap`, which named ten constructors to walk for it.

**The rule was not a limit.** `examples/nestedsum.vyrn` writes every nesting the
rule refused — `Option<Option<String>>`, `Result<Option<String>, String>`,
`Option<Result<String, String>>`, an `Array` of nested sums, and each of `?`,
`??`, `if let` and `match` over one. With the three refusals deleted and NO
other change, the interpreter, the native binary and the wasm module print the
same thirteen lines. The inner sum is 24 bytes, wider than a payload word, so
both compiled engines box it through the `_ =>` arm they already had for a
record.

**The rule was also not enforced.** `Map<K, Option<V>>.at(k)` answers
`Option<Option<V>>`, and it compiled on all three engines before this change —
verified against the branch point's own binary. So the refusal blocked the
SPELLING `Some(x)` and let the same type in through a builtin. A user enum of
the same shape (`examples/enumarray.vyrn`'s `Bag`) was never refused at all.
That asymmetry is exactly what §5.5 is about, and it is the half of it that
costs nothing to remove.

**The wire keeps its own refusal.** `codec::wire` declines `Option<Option<U>>`
independently of the checker, because a double `null` has two readings.
`toJson` of a record holding one still reports "not a codable type". `std/json`
and `std/jsondec` are unchanged; their doc comments now cite the codec instead
of the checker.

**Priced.** 16 mentions across ten constructors (§3's note), one function, one
diagnostic, three unit tests inverted from refusal to acceptance, one corpus
example added. Zero bytes: `VYRN_WASM_MANIFEST=check` is unchanged, and the
parity suite compares the same output it did before.

### 8.8 Two defects the probes found, not taken here

- **`movecheck` treats a nullary constructor as a binding.** `take(None)` twice
  reports "`None` is used here but was already consumed"; so does `take(Nothing)`
  for a user enum's nullary variant. It reproduces at the branch point, it is
  not about nesting, and it is not about the built-in sums either — a nullary
  constructor is a value with no owner and the move checker reads it as a name.
- **`vyrn why --memory` calls a `??` result's type "unknown".** The verdict is
  right (`Option<Int64>` owns no heap) and the reason is not. The `??` desugar
  runs in the parser, so the reporter has no recorded type for the expression it
  produces. **Taken, 2026-09-05.** The verdict was not always right either: a
  `let t = s ?? "y"` of `String` was called "unknown … owns no heap" and its
  release row went unreported. `declared::type_of` now reads the `match` the
  parser spells for `??` with the one rule it already had for `?`
  (`success_payload`): the scrutinee's `Option<T>`, `Result<T, _>` or Fallible
  `success` payload. Pinned by `why_memory_types_a_nullish_result_as_its_payload`.
  produces.

### 8.9 M2, taken: one payload encoding per engine

§8.4's rule is in both compiled engines. A sum's tag is an `i64`, its slot count
is its widest variant's payload WIDTH, and one pair of functions per engine
encodes every payload — built-in sum and declared enum alike.

**What each engine lost.** `box_payload` and `unbox_payload` folded into
`encode_payload` and `decode_payload`, which now answer a SLICE of words rather
than a pair. `word1` folded into `word2`. `build_sum2` and `build_enum` became
one `build_variant`, and `build_sum2` is the four-line call that names the
built-in sums' single payload. `enum_arity` had no caller left and went with
them. That is five functions for the four §8.6 predicted.

**The shape rule, and the one place it does not read as §8.4 writes it.** §8.4
says `words(t)` is 2 when `llt(t)` is `{ i64, i64 }`. `llt_of` of a sum now ASKS
`words` about its payloads, so asking `llt_of` back from `words` is a loop the
moment a type reaches itself — `type R = { a: Int64, b: Option<R> }` is legal and
overflowed the stack on `examples/container.vyrn`. So `payload_words_of` is a
structural test: a stored `fn`, a `lazy`, and a record of exactly two words. The
two readings differ in one place and §8.7 already measured it — a payload that is
itself a ONE-SLOT SUM prints `{ i64, i64 }` and is boxed, as it was before.
Nothing else prints that shape.

**Two things the step needed that §8.4 did not name.**

- **A sum can now have more than one shape, so a crossing between them is a
  rung.** `Rung::Reshape`: the tag, then the slots both shapes have, then zeros.
  Two callers make it unavoidable. A bare `None` is typed `Option<Int64>` and
  reaches an `Option<fn(Int64)>` slot, which is one word wider. And a GENERIC
  enum's slot count follows its type argument, so `Validation<Unit>` — what
  `applied_type` builds when a constructor cannot solve the parameter — is a
  narrower shape than `Validation<Point>`; four corpus programs reached that
  through `fromJson`. The plan decides it on the variant NAMES, so two
  instantiations of one enum qualify and two different enums of equal width do
  not. `coerce_plan` states it once and each emitter writes it: 49 code lines
  became 54, the native ladder 111 became 118, the direct one 169 became 192.
- **`?` needs the same shape check in both engines.** The propagated value is the
  whole sum, byte for byte, so the operand's sum and the function's must lower
  alike. The direct backend has checked that since RFC-0077 M5, where the
  textual one relied on every sum being 24 bytes. It checks now, in the same
  words. No corpus program reaches the refusal.

**§8.3's three probes, before and after.** The programs are the section's own,
read out of the emitted IR:

| probe | before | after |
|---|---|---|
| `Array<Option<Int64>, 3>` | `[3 x { i1, i64, i64 }]`, 72 bytes | `[3 x { i64, i64 }]`, 48 bytes |
| `Array<Maybe, 3>` | `[3 x { i64, i64 }]`, 48 bytes | unchanged |
| `Option<IntSink>` | `{ i1, i64, i64 }`, no heap | `{ i64, i64, i64 }`, no heap |
| `HasSink(IntSink)` | `{ i64, i64 }`, one malloc and one free | `{ i64, i64, i64 }`, no heap |
| `Option<String>` | `{ i1, i64, i64 }`, 24 bytes, no heap | `{ i64, i64 }`, 16 bytes, no heap |
| `HasWord(String)` | `{ i64, i64 }`, one malloc | `{ i64, i64 }`, no heap |

Every row is §8.4's table. The array of a built-in sum is a third smaller. The
enum's `String` payload and its stored `fn` each lost a heap round trip, and the
one row that grew is the enum's `fn`, by 8 bytes, exactly as priced.

**The bytes.** `rfcs/census/wasm-sha256.tsv` is regenerated in this commit and no
other: 143 of its 174 rows moved, and the 31 that did not are the programs with
no sum in them. Parity is 41 of 41 byte-identical on three engines.

**Priced.** Five functions, and 55 code lines out of `vyrn-codegen` — 58 out of
the textual emitter, 3 back into the direct one. The comment lines rose by 128,
which is the rule being written down where two literals used to stand. §3's
counts moved with it: 2,491 mentions became 2,505, because `Option` and `Result`
are now ASKED for their shape in `native` where the shape used to be a string
literal, and `Fn` is named four times less because the payload rule no longer
names it.

### 8.10 M3, taken: a pattern names a variant, and the scrutinee says what it means

`Pattern::Some`, `Pattern::None`, `Pattern::Ok` and `Pattern::Err` are gone.
`Some(x)`, `None`, `Ok(x)` and `Err(e)` parse as `Pattern::Variant`, which is
what `Circle(r)` and `Empty` already parsed as. The parser loses the four-arm
`match` on the name and the `pattern_binding` helper that went with it: an
identifier followed by an optional parenthesised binder list is one production,
and it always was.

**The scrutinee is what says a name is a tag**, and every consumer already had
it. The checker's `match` and `if let` both mapped a pattern to `(tag, bind)`
and then compared the tag against the scrutinee's two — `Variant(v, binds)` is
that pair, with no arm to write. The interpreter's `match_pattern` tests a
pattern against a VALUE, so `Val::Option(Some(v))` decides that `Some` names its
tag, beside the `Val::Enum` arm that already decided the same thing for a
declared variant. Both backends read the tag through `pattern_is_one`, which now
asks about a name.

**`Success` and `Failure` stay**, and §8.6 said why: the `??` desugar runs in the
parser, names a TAG rather than a variant, and nothing else can name a tag before
the checker runs. They are two arms in the four places that read a pattern's
binders and one arm each in the two that read its tag.

**One rule moved out of the parser.** A built-in sum's arity was a parse rule —
`pattern_binding` ate exactly one `(name)` — and it is now a check, because the
production that replaces it accepts any arity. `sum_arm_arity` states it once for
both `match` and `if let`: `None` binds nothing, the other three bind one. A
declared enum states its arity in its declaration and is checked against that;
these four have no declaration, which is the whole reason the rule needs a home.
`Some(x, y)` reports "variant `Some` has 1 payload(s), but the pattern binds 2",
which is the wording a declared enum's wrong arity already had.

**One walk needed telling.** The loader collects the free names of a body, and a
variant pattern's head is a reference to a declaration. These four refer to
nothing, so `is_sum_arm` names them and the walk skips them. It is the same
guard §8.5 predicted for the constructors, arriving one step early.

**Priced.** Four constructors of `ast::Pattern`, 8 down to 4. **89 mentions of
the four across the compiler, down to 0.** 19 code lines, one parser function
deleted and two small ones added — the arity rule and the free-name guard, each
one place where there had been none. Zero bytes:
`VYRN_WASM_MANIFEST=check` is unchanged and parity is 41 of 41.

### 8.11 M4 and M5, not taken: they are one step, and it is not zero bytes

§8.6 splits the rest of the collapse in two: M4 makes `resolve` answer `Enum`
with no byte moving, and M5 deletes the constructors. Both halves were tried on
this branch and neither holds as written. The step is one step, it needs a third
one in front of it, and the reason is not in the arms.

**What was tried.** One arm in `types::resolve_d`, exactly the shape the `lazy`
arm beside it has:

```
Type::Option(inner) => Type::Enum([ None(), Some(inner) ])
Type::Result(ok, err) => Type::Enum([ Err(err), Ok(ok) ])
```

The compiler builds. **97 of `vyrn-frontend`'s 1,186 unit tests turn red on that
line alone.** Two consumer fixes — `None`'s inference from its expected type, and
the `match` scrutinee's dispatch, both in `checker.rs` — take it to 45, spread
over `checker`, `interp`, `codec`, `jsondec`, `loader`, `own` and `schema`. The
two codegen crates were not reached.

**Why the `lazy` precedent does not transfer.** RFC-0085 M4a's own note says why
that arm was free: it does not reach a record's fields, and three places read the
marker. The two sums are read on RESOLVED values everywhere. Counted as
match-arm positions on `Type::Option`/`Type::Result`:

| file | arm positions |
|---|---|
| `vyrn-codegen/src/lib.rs` | 37 |
| `vyrn-frontend/src/checker.rs` | 29 |
| `vyrn-codegen/src/direct.rs` | 13 |
| `vyrn-frontend/src/codec.rs` | 7 |
| `vyrn-frontend/src/own.rs` | 5 |
| `vyrn-lower/src/core.rs` | 4 |
| `vyrn-frontend/src/interp.rs` | 3 |
| `vyrn-frontend/src/movecheck.rs` | 3 |

101 arms, before the `matches!` and `if let` spellings. Not all read a resolved
type, and every one has to be read to find out which. That is M5's own 205, done
at M4 — which is the first half of the finding: **the two steps are one.**

**The zero-byte requirement fails, and not on the arms.** `own::release_kind`
records a drop with the RESOLVED type. So an `Option<String>` binding's row stops
being `Deep(Option(String))` and becomes
`Deep(Enum([None, Some(String)]))` — measured, at `own.rs`'s own unit test for
that row. Both emitters then route the row to their ENUM release, and the two
paths are not the same bytes:

| the sum's path | the enum's path |
|---|---|
| `Gen::release_sum`, labels `rel.sum.*`, arms in the caller's order | `Gen::release_enum`, labels `rel.enum.*`, variants in tag order |
| `Gen::copy_sum`, labels `cp.sum.*` | `Gen::copy_enum`, labels `cp.enum.*` |
| `Gen::gen_match_body_boxed`, a two-way `br` on `icmp eq i64 %tag, 1` | `Gen::gen_match_enum`, a `switch i64` |
| `Fn_::rel_at`'s `Option`/`Result` arms, one `If` | its `Enum` arm, one `If` per variant |

§8.9 made the ENCODING one. It did not make the EMISSION one, and §8.6 assumed
it had.

**The order that works**, and the correction to §8.6:

- **M4a — one emission per engine.** Unify release, copy and match so a built-in
  sum and a two-variant enum produce the same instructions. This MOVES bytes and
  regenerates the manifest, which is why it cannot sit behind M4's zero-byte
  promise. **Taken, 2026-09-05 — §8.12.**
- **M4b — `resolve` answers `Enum`**, and every consumer reads a sum through one
  pair of readers instead of matching a shape that depends on whether its
  scrutinee was resolved. The probe wrote the readers and they are four lines
  each: `option_payload(ty) -> Option<&Type>` and
  `result_payloads(ty) -> Option<(&Type, &Type)>`, each answering for the surface
  constructor and for the enum form. They are not in the tree — unused code is
  debt — and this is where they are written down.
  **Taken, 2026-09-05 — §8.13.**
- **M5 — delete the constructors**, with §8.6's three guards unchanged.

**One thing §8.6 gets wrong about the risk.** It says `solve_param` "has no
`Type::Enum` arm" and calls that the step's whole risk. It has one, and it
matches variant by name then payload-wise, so the parameter a generic
`Option<T>` carries is solved once the enum arrives. What it lacks is the CROSS
arm `Lazy` already has — `Type::Option(p)` binding from an `aty` that arrives as
the enum, and `Type::Enum(pv)` binding from an `aty` still spelled
`Option`/`Result` — because after M4b the two spellings meet at a call boundary.

**One drift §8.9 left, recorded and not fixed.** `own::owns_heap`'s `Option` and
`Result` arms say they "mirror the emitter's `payload_boxed`" and name the word
class by hand — `Int`, `Bool`, `Str`, `Fn`. Since §8.9 `payload_boxed` is
`words(t) == 1 && llt(t) != "i64"`, so a two-word payload — a record of two
`Int64`s — rides inline and `owns_heap` still calls it heap-owning. It costs
nothing today: the row it registers walks a payload that owns nothing and frees
no box, and parity, the residue ratchet and the memory suite are all green with
it. It is one rule stated twice, and M4a is where it stops being.

### 8.12 M4a, taken: one emission per engine

§8.9 made the ENCODING one. This makes the WALK over it one. A built-in sum and
a declared enum of the same variants now emit the same instructions on both
compiled engines, for a release, for a copy and for a `match`.

**One list, asked for.** `sum_variants_of` answers the variants of any sum in
TAG order: `Option<T>` is `| None | Some(T)` and `Result<T, E>` is
`| Err(E) | Ok(T)`, which is §8.1's table and the declaration each would carry if
it had one. Both emitters ask it — `Gen::sum_vs` and `Cx::sum_vs` — and neither
matches the spelling any more.

**What each engine lost.** In the textual emitter `release_sum` folded into
`release_enum` and `copy_sum` into `copy_enum`, and the survivors took the
`sum` name because they now serve every sum. `gen_match_body_boxed` folded into
`gen_match_enum`, which is `gen_match_sum`; `gen_arm_body`, which existed only to
bind the one payload of a built-in sum, had no caller left. That is four
functions. In the direct backend `rel_at` and `copy_at` each lost their `Option`
and `Result` arms to their `Enum` arm — four arms, and one of them was the
`if`/`else` a `Result` took where an enum takes one `if` per variant.

**The tag is a position, not a name.** `release_enum` read a variant's tag out of
the module-wide `variants` map, keyed by variant NAME. A built-in sum's variants
are in no declaration and so in no such table, and two declared enums that share
a variant name collided in it. The tag is the variant's index in the list, which
is what the layout means; it is now read that way, and the map has one reader
fewer.

**`Success` and `Failure` reach the switch.** §8.10 kept them: `??`'s desugar
runs in the parser and names a TAG. `gen_match_sum` maps them to tag 1 and tag 0
and binds one name each, which is the rule the deleted path stated by picking the
tag-1 arm with `pattern_is_one`. A `Failure` over an `Option` still binds a dead
word — variant `None` has no payload — because that is cheaper than teaching a
parser desugar about types, and it is what the built-in path already did.

**The one rule §8.11 recorded, closed.** `own::owns_heap` named the payload word
class by hand, four times, as `Int`, `Bool`, `Str`, `Fn`. That list ran two rules
together — a payload two words WIDE rides in its slots, and a one-word payload
rides in the word when the word is what it is — and §8.9 moved the first of them,
so a `lazy` and a record of two `Int64`s were called heap-owning where the
emitter puts them inline. `types::payload_words` and `types::payload_boxed` state
both rules once, in the frontend, and `own` and the two emitters ask. The two
answers differ at one type the emitter names and the language cannot — `Code` on
the generator-host path, which lowers to `i64` — and there the frontend answers
the conservative "boxed", which registers a release row that frees nothing.

**§8.3's probes, unmoved.** M4a changes no shape and no encoding, and the probes
say so: `Array<Option<Int64>, 3>` is `[3 x { i64, i64 }]` and `Array<Maybe, 3>`
is the same; `Option<IntSink>` and `HasSink(IntSink)` are both
`{ i64, i64, i64 }` with no heap; `Option<String>` and `HasWord(String)` are both
`{ i64, i64 }` with no heap. Every row is §8.9's after column.

**The bytes.** `rfcs/census/wasm-sha256.tsv` is regenerated in this commit and no
other: **25 of its 173 rows moved**, and every one of them is a program whose
release or copy walks a `Result` — the arm order and the `if`/`else` are what
changed in the wasm. The textual emitter's own churn is labels and block order,
which the manifest cannot see, so the number is smaller than §8.9's 143. Parity
is 41 of 41 byte-identical on three engines; the residue ratchet and the memory
suite are green.

**Priced.** Four functions and four arms. **224 code lines net** —
`vyrn-codegen` −216 (the textual emitter −173, the direct one −43) and
`vyrn-frontend` −8, which is `own` −36 against `types` +28 for the two rules that
moved in. §3's counts moved by one: `Option` and `Result` each fall by one in
`native` because a walk asks for a variant list where it used to name the
spelling, and `types` rises by 13 for the rules that arrived.

### 8.13 M4b, taken: `resolve` answers `Enum`, and it cost no bytes

`types::resolve` answers `| None | Some(T)` for an `Option<T>` and
`| Err(E) | Ok(T)` for a `Result<T, E>`. One arm, beside the `lazy` arm §8.6
compared it to, and §8.11 is right that the comparison does not transfer: the two
sums are read on resolved values everywhere, so the arm alone turns **101 of
`vyrn-frontend`'s 1,177 unit tests red**.

**The readers, and what they replaced.** `option_payload` and `result_payloads`
are §8.11's four-liners, and they are in the tree now: each answers for the
surface constructor and for the enum form, so a consumer never has to know which
it was handed. Every site that matched a resolved sum's SPELLING asks one of them
instead. What made the step tractable is that a consumer usually did not need a
reader at all — its `Type::Enum` arm was already there and already said the same
thing, and the sum's own arm beside it was the duplicate. `own::owns_heap`,
`own::release_kind`, `checker::declared_owned_in` and `movecheck::payload_binding`
each lost an arm that way.

**Four consumers were a merge, not a reader.**

- **`check_match` is `check_match_enum`.** It dispatched to the enum checker
  first and then ran a two-tag path of its own — a `want` table, an arm loop, its
  own exhaustiveness message. Since `base` answers `Enum`, an `Option` scrutinee
  reaches the enum checker, so the sixty lines behind it are gone and a built-in
  sum gets the wording a declared enum already had: "`Ok` is not a variant of
  `Option<Int64>`" where it used to say "pattern `Ok` does not match scrutinee",
  and "`match` is missing variant `None`" for "`match` must cover both". Three
  unit tests carried the old words and nothing else did.
- **The direct backend's `Sum` is a variant list.** `enum Sum { Opt, Res, Enum }`
  was the split in that engine, and `sum_of` answers `Enum` for everything now, so
  the type is `Vec<EnumVariant>`. `pattern_binds` and `tag_test` lost their
  built-in arms; `try_` reads tag 1 as the success side of any two-variant sum,
  which is what §8.1 says a tag order is for.
- **`?` is not `Fallible` just because it resolves to an enum.**
  `vyrn-lower`'s `Expr::Try` routed a `Type::Enum` scrutinee to RFC-0080's
  declared-`Fallible` path. After the arm that is every `?`, so the test is WHICH
  variant list it is, not whether there is one. `examples/nestedsum.vyrn` is what
  said so, at the kernel, as a use-after-release.
- **`normalize_fn_sig` has to descend into a sum's payloads.** It normalized
  `Option<T>`'s payload through its own arm; with the arm gone it stopped at the
  variant list, so a stream step registered its tag under an unnormalized payload
  and the dispatcher looked one up under a normalized one — `internal: invalid
  function value` on five corpus programs. The direct backend's two stream
  dispatchers were keyed on a RAW `stream_step_sig` as well, where the textual one
  had normalized since RFC-0077; both normalize now.

**§8.6's third guard, arriving with the step rather than after it.** Two of the
three guards M5 predicts are already needed here, because a resolved sum reaches
a user:

- **`codec::wire` keeps `Wire::Option` and `null`**, and lists `Ok` first,
  because a wire tag is a NAME and not an index. It reads the resolved type
  through the two readers before its `Enum` arm.
- **`Display` keeps printing `Option<T>` and `Result<T, E>`.** Without it a
  release row in `vyrn emit-lowered` read `Deep<enum { None | Some }>`, and every
  diagnostic that names a resolved sum would have named a shape at a user who
  wrote a name.

The third guard — the parser accepting `Some`/`Ok`/`Err` with no declaration — is
untouched and is M5's.

**Zero bytes, and the one place it nearly was not.**
`VYRN_WASM_MANIFEST=check` is unchanged on all 173 examples, parity is 41 of 41,
and the residue ratchet is green. Two attempts moved bytes and were tightened
back rather than accepted:

- `movecheck::payload_binding` types `??`'s binder on a `Result` and not on an
  `Option`. Reading it through one variant list types both, which is right and is
  the same defect §8.8 fixed in `declared::type_of` — and it moved
  `nestedsum.vyrn`'s wasm. **Recorded, not taken**: the arm keeps the `Result`-only
  reading, and the fix belongs with a step that is allowed to move bytes.
- `check_match_enum` accepting `??`'s pair on any two-variant enum would widen
  the surface. It accepts it only on the two built-in variant lists, so `??` on a
  declared two-variant enum is refused in the same words as before.

**Two test helpers had the same duplicate arm.** `tests/lowered.rs`'s `deep`
resolves at every level and had no `Enum` arm, so an alias whose payload is a name
stopped comparing equal after resolution; its `defaulted` compared `Result`
against `Result` and not variant list against variant list. Six cross-backend
classes appeared, all of them the helper's blind spot rather than a disagreement.
Both walk sums now.

**Priced.** **101 red tests to 0.** `Option` falls from 111 mentions to 90 and
`Result` from 103 to 90 across §3's seven files; `Enum` rises from 57 to 65, and
the total falls 2,504 to 2,478. One `enum` deleted (`direct::Sum`), one function
deleted (`check_match`'s two-tag body, folded into `check_match_enum`), and two
added — the readers. **42 code lines net INTO the compiler**, which is the honest
number: `checker` gives up 55 and `vyrn-lower` 4, and the readers, the two guards
and the two normalizations cost more than that in `types`, `ast`, `codec` and the
two emitters. M4b buys a constructor's DELETION, which is M5's line, not its own.

**One consumer was missed, and the workspace could not say so.** The generation
engine (`vyrn-genwasm`) is EXCLUDED from the workspace, for the reason
`compiler/Cargo.toml` gives: it carries an embedded wasmtime and the language
builds and tests without it. So `cargo test --workspace` never compiles it, and a
dead arm in it is not a compile error and not a red test — it is the exact
failure mode the readers exist to prevent, at the one crate no workspace gate
reads.

Both ends of the reflection channel matched a RESOLVED sum's spelling.
`encode`, which walks the host's literal into atoms, and `Decoders::materialize`,
which synthesizes the guest's decoder for the same type, each had a
`Type::Option(inner)` arm under a `match resolve(..)`. After M4b neither arm can
be taken. The decoder's fell to `_ => return None`, so `reflect_entries` answered
`None`, so the wrapper program could not be synthesized and the engine DECLINED:
**12 of the 25 generator examples silently ran on the interpreter**, which is the
one thing `tests/genwasm.rs` exists to catch. With the decoder repaired and the
encoder still dead the atom stream desynchronized and the guest trapped, which is
why the two are one defect and not two.

Both read `option_payload` now, and the comment on each names the other: the two
sides agree because they walk one type through one reader, not because each
remembers the same convention. `genwasm` is green on 25 of 25, byte-identical
across engines. **The lesson is the census's own**: §3 counts seven files, and
this arm was in none of them, so nothing in the collapse's own measurement could
have predicted it. An excluded crate needs its gate named in the step, not in CI.

### 8.14 M5, not taken: a declaration is what does not survive the deletion

M5 was tried on this branch and reverted. Unlike M4b it is compiler-CHECKED —
deleting `Type::Option` and `Type::Result` from `ast::Type` is an error at every
remaining site, not a silently-taken wrong arm — so what stopped it is not risk.
It is that one of the sites is not a site at all.

**The mechanical half, measured.** 268 mentions of the two constructors across
21 files (270 before §8.13's late defect took two dead arms out of
`vyrn-genwasm`). **115 of them are `Type::<Sum>(Box::new(..))` constructions**, and a
paren-matching rewrite turns every one into `Type::option(t)` / `Type::result(ok,
err)` — two associated functions on `Type` that build §8.1's variant lists. That
is §8.5's warning arriving exactly as written: the census stops counting a
construction the moment it hides behind a helper, and nothing simplifies. The
honest reading of M5's number is the same as §8.5's — about 150 arms, not 205,
and not 270.

**What is left after the rewrite: 100 compile errors.** Most are a dead arm to
delete, because the `Type::Enum` arm beside it already says the same thing —
`collect_params`, `contains_stream`, `contains_fn`, `ensure_type_exists`,
`region_dangles`. Three are a RULE to rewrite rather than remove:

- **`assignable`'s covariance.** Two rules — an `Option` in its payload, a
  `Result` in both — become one rule over a variant list, and a declared enum
  gains a covariance it did not have. That is the collapse and it is a surface
  change, so it needs its own line in a release note.
- **`check_try`.** `?` matches the operand's spelling on an UNRESOLVED type, so
  it takes the readers rather than the enum arm; and `Fallible` sits under the
  same `match`, which is the arm the readers have to run in front of.
- **`check_match`'s alias branch has to move above the enum branch.** They test
  the same `Type::Enum` now, and the alias is the one that declares no names.

**And one that is not a site.** `type Maybe = Option<Int64>` and
`type Maybe = | None | Some(Int64)` become the SAME `TypeDecl.base`. **Twenty
places read a declaration's base as `Type::Enum`** — the checker's declaration
check and its two scrutinee resolvers, five collections in `loader`, three in
`symbols`, `interp` twice, `codec`, `declared`, `own`, `vyrn-lower`'s constructor
lookup, and the module-wide `variants` maps in both emitters. Every one of them
would read an ALIAS as a variant declaration and register `None`, `Some`, `Ok`
and `Err` as variants of it.

That is not hypothetical. The corpus holds **seven such aliases** —
`examples/aliascontext.vyrn`'s `MaybeAge`, `examples/enumcodec.vyrn`'s `Lookup`,
and five `*Result` aliases in the shared wire modules of four separate projects,
two of them both named `DeleteResult`. `vyrn-codegen`'s `variants` map is keyed
by variant NAME across the whole module, so `Ok` and `Err` would each resolve to
whichever alias was collected last.

**So §8.6's third guard is not one guard.** It says "the parser keeps
`Some`/`Ok`/`Err` as declaration-free constructor names", which is true and is
already how the parser works. What M5 actually needs is the same guard on the
other side: **a declaration whose base is one of the two built-in variant lists
is not a variant declaration**, stated once and asked at each of the twenty
readers — the shape §8.13 already used for `codec::wire` and `Display`, at
twenty sites instead of two.

**What M5 needs, in order.** One reader — `is_sum_alias(decl) -> bool`, or the
readers asked of `d.base` — and twenty call sites; then the 115 constructions;
then the 100 errors, of which three are the rules above. It is zero bytes if the
guard is right and a name collision across four corpus projects if it is not,
which is why it is a step and not a rename.

**And the argument FOR taking it, from this branch's own defect.** §8.13 records
a dead arm that survived every gate the workspace runs, at both ends of
`vyrn-genwasm`'s reflection channel, and it cost 12 of 25 generator examples
their engine without one red test. M5 is the step that makes that class of miss
impossible: with the constructors gone, an arm that can no longer be taken does
not compile. The excluded crate is the sharpest case, because it is the one the
workspace cannot type-check at all — so the deletion reaches it where a reader
convention did not.
