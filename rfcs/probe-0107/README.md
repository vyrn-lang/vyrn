# probe-0107 — the RFC-0107 M0 feasibility probe

One program per question, in the `census-0103` / `bench-0104` style: the answer
is the program's output or the diagnostic it fails with, not a reading of the
compiler. Nothing here ships a feature, and nothing here touches `std/`,
`compiler/` or `site/` — the `.vyx` compiler's part is played by a stand-in
generator in `probes.vyrn`.

The question M0 was given: can the `.vyx` generator, inside the comptime sandbox,
**today, with no compiler changes** — (a) load and evaluate a provider module
named by the *template* rather than by the generator's own imports, (b) call an
exported function of it with the tag's attributes and get `Html` back, (c) have
every file the provider reads recorded so the gen cache stays sound, (d) turn a
provider error into a diagnostic positioned at the tag?

## The cast

| file | what it is |
| --- | --- |
| `provider.vyrn` | the toy provider: `glyphs(dir, names)` / `glyphsAt(dir, names, file, line, col)`, ordinary comptime-pure Vyrn, knows nothing about `.vyx` |
| `data/collection.txt` | the "pinned collection": `name=body` lines (a JSON reader would only lengthen the transcript) |
| `probes.vyrn` | the probe generators, including `p7Vyx` — the `.vyx` compiler's part in miniature |
| `probe-p2.vyrn` | P2a, alone, because it deliberately does not compile |
| `vyxtag/Badge.vyx`, `vyxcomp/Plain.vyx` | real `.vyx` components compiled by the SHIPPED `std/vyx` |
| `Badge.vyx`, `BadgeTypo.vyx` | templates read by `p7Vyx` |
| `vyrn.json` | two `dependencies` aliases, for the alias question |

Run everything from this directory with a built `vyrn`.

## P0 — what `std/vyx` does today

`vyrn run p0a-tag-today.vyrn` — `vyxtag/Badge.vyx` imports the provider in its
`<script>` and writes `<Icon name="github"/>`:

```
vyxtag/Badge.vyx:8:1: `<Icon>` names no component — a component is a `.vyx` file in the same directory, or one this `<script>` imports
  note: in generated code generated by components("./vyxtag") at p0a-tag-today.vyrn:1 (see `vyrn emit-gen`)
```

`vyrn run p0b-provider-today.vyrn` — the same provider reaching the same
template with no tag, through a `<script>` generator import and `v-html`:

```
<span class="badge"><svg>M2 2 H14 V14 H2 Z</svg></span>
```

That is the shipped `std/vyx`, the shipped loader, and no patch anywhere. A
generation-time provider already reaches a template; only the tag syntax is
missing.

An earlier arrangement of the same two components produced one more fact worth
keeping, because it is a constraint on M1:

```
generated by components("./vyxcomp") at p0a-tag-today.vyrn:1:0: `./vyxcomp/Plain.vyx` imports `g` from `glyphs("./vyxcomp/../data", "discord")`, and a sibling component already binds that name to `glyphs("./vyxcomp/../data", "github")` — one namespace alias reaches one module across the whole set, so rename one of them
```

Two components in one directory cannot both bind `g` to the same provider with
different arguments. A per-tag emission scheme has to mint its own namespace
names (as `p7Vyx` does: `g0`, `g1`), never reuse the author's.

## P1 — can the generator read the provider the template named?

`vyrn run p1a-escape-read.vyrn` (`readFile`) and `p1b-escape-reflect.vyrn`
(`moduleInterface`), where `./data` is the generator's only path argument and
`../provider.vyrn` is what the template imported:

```
p1a-escape-read.vyrn:4:0: generator `p1EscapeRead("./data")` failed: generator read `./data/../provider.vyrn` escapes its declared inputs (data, data.vyrn) — a generator may only read under its constant path arguments
p1b-escape-reflect.vyrn:3:0: generator `p1EscapeReflect("./data")` failed: generator read `./data/../provider.vyrn` escapes its declared inputs (data, data.vyrn) — a generator may only read under its constant path arguments
```

The sandbox's input roots are the generator call's own constant string arguments
(`loader.rs`, "Each constant string path argument becomes an allowed input
root"). A path discovered while reading a template is not one of them.

`vyrn run p1c-reflect.vyrn` — the same reflection when the provider IS one of the
generator's arguments (`p1Reflect("./provider")`):

```
glyphs(dir: String, names: String) -> String
glyphsAt(dir: String, names: String, anchorFile: String, line: Int64, col: Int64) -> String
```

So reflection of a provider is available exactly when the provider is *declared
at the generator call site*, and what it yields is names and type spellings.

## P2 — can the generator call it?

`vyrn run p2a-call.vyrn` asks `FnInfo` for the member that would make the design
in RFC-0107's "The design" section work:

```
p2a-call.vyrn:10:0: call to unknown function `call`
p2a-call.vyrn:7:15: function `p2Call` must return String on all paths
```

`vyrn run p2b-fn-arg.vyrn` tries the other shape — hand the generator the
provider itself instead of a name to load:

```
p2b-fn-arg.vyrn:5:0: generator import `p3Nested(..)` needs compile-time-constant arguments (v1: string / integer / boolean literals)
```

The mediated set inside a `gen fn` is exactly `readFile`, `listDir`,
`moduleInterface` (`checker.rs:208-211`). None of them evaluates anything, and a
generator's arguments are constants, so a provider can only ever be named by a
string.

## P3 / P7 — deferred evaluation, which does work

The generator does not have to evaluate the provider. It can EMIT the import.
`vyrn run p3-nested.vyrn`:

```
<svg>M8 0 L16 8 L8 16 Z</svg><svg>M2 2 H14 V14 H2 Z</svg>
```

`p7Vyx` does the same from a real template file: it reads `Badge.vyx` (its own
path argument), takes the provider spec its `<script>` imported and the glyphs
its tags named, and emits one provider import per tag carrying the tag's own
position. `vyrn run p7-vyx.vyrn` prints the two glyphs, and `vyrn emit-gen
p7-vyx.vyrn` shows the whole chain:

```
// ==== generated by glyphsAt("./data", "github", "./Badge.vyx", 7, 5) at generated by p7Vyx("./Badge.vyx") at p7-vyx.vyrn ====
/// Generated by the RFC-0107 M0 probe provider — do not edit.
import { el, text, Html } from "std/html"
export fn github() -> Html {
    return el("svg", [], [text("M8 0 L16 8 L8 16 Z")])
}
...
// ==== generated by p7Vyx("./Badge.vyx") at p7-vyx.vyrn ====
/// Emitted by the RFC-0107 M0 probe from ./Badge.vyx — do not edit.
import { toHtmlString, Html } from "std/html"
import { glyphsAt } from "./provider"
import * as g0 from glyphsAt("./data", "github", "./Badge.vyx", 7, 5)
import * as g1 from glyphsAt("./data", "discord", "./Badge.vyx", 8, 5)
export fn page() -> String {
    let mut parts = ""
    parts = parts + toHtmlString(g0.github())
    parts = parts + toHtmlString(g1.discord())
    return parts
}
```

A generation whose output is an import line is a generation the loader will
follow, and the provider runs in its own sandbox with its own input roots.

## P4 — cache soundness

On the `p3-nested` chain and on the shipped-`std/vyx` chain (`p0b`) alike,
counting entries written under `~/.vyrn/cache/gen`:

```
run 1                                   -> 3 entries written
run 2, nothing changed                  -> 0 entries written
edit data/collection.txt, run 3         -> <svg>M9 9 L1 1 Z</svg><svg>M2 2 H14 V14 H2 Z</svg>   (1 entry written)
restore it, wait, run 4                 -> 0 entries written
```

The provider's `readFile` is recorded in the provider generation's own entry, so
the edit invalidates exactly that entry and the outer generation (whose output is
one import line) stays a hit.

## P7b — the diagnostic

`BadgeTypo.vyx` misspells the glyph. `vyrn run p7b-diagnostic.vyrn`:

```
BadgeTypo.vyx:7:5: the collection under `./data` has no glyph `githup` — nearest is `github`
  note: in generated code generated by glyphsAt("./data", "githup", "./BadgeTypo.vyx", 7, 5) at generated by p7Vyx("./BadgeTypo.vyx") at p7b-diagnostic.vyrn:3 (see `vyrn emit-gen`)
```

Line 7, column 5, is the tag. The provider never read that file: `std/diag`'s
`report` anchors wherever the generator says, and the position travelled to it as
two ordinary integer arguments.

## P6 — the alias question

`vyrn.json` here declares `"coll": "./data"` and `"prov": "./provider"`.

```
vyrn run p6-alias.vyrn         -> readFile said: cannot read `coll/collection.txt`
vyrn run p6b-alias-import.vyrn -> <svg>M8 0 L16 8 L8 16 Z</svg>
vyrn run p6c-alias-reflect.vyrn -> p6c-alias-reflect.vyrn:3:0: generator `p1Reflect("prov")` failed: moduleInterface cannot read `prov`: The system cannot find the file specified. (os error 2)
```

An aliased MODULE specifier works everywhere, including as the target of a
generator import inside generated source. An aliased DATA path does not: the
mediated `readFile`/`moduleInterface` resolve their argument by path arithmetic
against the importer's directory (`gen_scoped_path`), with no import-map step.

## One contradiction found on the way

P2a's diagnostic reads `p2a-call.vyrn:10:0`, and the error is at
`probe-p2.vyrn:10`. A checker error inside a generator MODULE is reported at the
importing file's path with the generator module's line number, so the path names
a file where that line says something else. Filed as a note, not fixed here.
