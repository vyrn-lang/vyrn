# Census — six language questions, now ruled

Six topics the owner asked about. Each file collects what other languages did, what it cost them, and what Vyrn already has that touches the question. Each ended with options, not a choice — and each now carries the ruling under its `## Decision (2026-08-28)` heading, made on the owner's "finish the design decisions": lambda syntax shipped as RFC-0110; literal unions stay the nominal enum (design A); coroutines are deferred whole, `spawn` standing, until wasm can suspend and a real program asks; attributes stay `gen fn` plus contextual keywords (option A); refinement subsumption fixes its line at the decidable core (options 1–2, never an SMT solver) and waits for a caller; operator protocols are the fixed direction on demand and the GPU backend stays closed with its price recorded.

## The index

| topic | file | how big the change would be | what it would break | fits Vyrn without a new solver or a new backend? |
|---|---|---|---|---|
| 1. lambda syntax | [lambda-syntax.md](lambda-syntax.md) | medium to large — a new syntax must be threaded through the lexer, parser, checker, formatter, interpreter, both compiled backends, the LSP, the site highlighter, the editor extension, the guide, and the docs; the current `|x|` syntax is consumed or produced in 14 locations across the compiler alone | every `.vyrn` file that uses a lambda (65842 matching lines across `std/`, `examples/`, `site/`, measured by `grep -rn '|[a-zA-Z_]' --include=*.vyrn`); the formatter output; the editor grammar; the guide examples | yes — no solver or backend needed; the `fn(x) { }` keyword form is unambiguous and needs no new token, no lookahead, and no backtrack (parser.rs:1289 already distinguishes `fn name(...)` from other forms); the `=>` and `->` forms collide with existing Vyrn tokens but are resolvable by context |
| 2. literal unions | [literal-unions.md](literal-unions.md) | medium — Vyrn already has nominal enums with payloads, exhaustive match, and match-time narrowing; the gap is (a) selecting a member by reading a user-visible discriminant field rather than by variant name, and (b) the array variance question | adding a discriminant field changes enum syntax and every match that destructures by name; making `Array` invariant breaks the existing covariance at checker.rs:2118, which programs in `std/` and `examples/` may rely on | yes — no solver or backend needed; the hard question is array variance, which is a type-system decision, not a solver or backend question; designs A and D dodge the variance problem by keeping variants non-standalone; design C closes it by making arrays invariant |
| 3. coroutines | [coroutines.md](coroutines.md) | large — Vyrn's `spawn` is a pure fork-join primitive, not a coroutine; a stackless `async`/`await` needs a new compiler pass (state machine transformation), function colouring, and a `Pin`-like answer for borrows across suspension; a stackful design needs a stack switch that wasm does not support today | every function that wants concurrent I/O changes signature (stackless); or native and wasm diverge in capability (stackful); the `spawn_safe` fixpoint widens from a purity proof to an effect system | partly — a stackless design (option B) needs no new backend and no solver, but needs a new lowering pass; a stackful design (option C) is blocked on wasm because the stack-switching proposal is at Phase 3 with no shipped browser or runtime (option D gates on it); option E reuses `gen` machinery but the gen host interface, cache, and sandbox are built for compile-time, not runtime scheduling |
| 4. attributes | [attributes.md](attributes.md) | small to medium — Vyrn has no attribute syntax today; 13 special-cased declaration modifiers each parsed by their own parser arm, sharing no grammar; the `wasm-export-name` named in the assignment is not a surface attribute but an LLVM IR string emitted by codegen (vyrn-codegen/src/lib.rs:4436) | an inert-only attribute grammar (option B) breaks nothing; a `gen fn` trigger attribute (option C) breaks nothing if it is pure sugar over the existing import path; a full active attribute system (option D) risks name collisions and needs splice semantics | yes — Vyrn's `gen fn` (RFC-0021) already provides sandboxed, deterministic, cached compile-time code; an attribute that runs a `gen fn` is a new attachment point, not a new mechanism; the sandbox rules (COMPTIME_FORBIDDEN at checker.rs:9478, check_comptime_purity at checker.rs:9502) need no change; no solver or backend needed |
| 5. refinement subsumption | [refinement-subsumption.md](refinement-subsumption.md) | medium — Vyrn has validated types (RFC-0003) with `where` predicates, `Validation<T>`, `Issue`, and `schemaOf`, but `assignable` uses strict name identity for predicated types (checker.rs:2126-2134) with no cross-type subsumption; DFA containment exists for string flows (regex.rs:834-885) but is not applied to general type-to-type subsumption | adding subsumption changes `assignable`, which every assignment, parameter passing, and type coercion goes through; the predicate extraction infrastructure (predicate_bounds, predicate_multiple_of, predicate_length_bounds, predicate_pattern) exists but is used only for reflection/schema emission | depends on the predicate class — character-set exclusion is a regular language containment question and is decidable without a solver (option 2, DFA subsumption); numeric range containment is decidable by interval arithmetic (option 1); an arbitrary condition function is not decidable and needs either an SMT solver (option 4) or user-declared subsumption with compiler verification (option 5); options 1, 2, and 3 need no solver and no backend |
| 6. operators and GPU | [operators-and-gpu.md](operators-and-gpu.md) | small for operator overloading (option A: operators as protocols, parser rewrite only — the static dispatch and monomorphization already exist per RFC-0084); large for GPU (option C: a third backend, priced by RFC-0101 at roughly a third of an existing backend) | operator protocols change the `Num`/`Ord`/`Eq` compiler-internal bounds, which every generic function using `<T: Num>` needs updated; GPU execution needs an allocation-forbidding check and a thread-index builtin that do not exist | operator overloading: yes — it is a protocol with syntax, and Vyrn protocols are already static and monomorphized (RFC-0084), so no solver or backend needed; GPU computing: no — a GPU backend is a third emitter (RFC-0101), which is a new backend; HVM4 is pre-launch with no published benchmarks and a single-threaded runtime, so it does not offer a shortcut |
